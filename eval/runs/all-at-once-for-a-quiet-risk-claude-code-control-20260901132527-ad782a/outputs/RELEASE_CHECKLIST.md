# Fee Rounding Release Checklist

Use this checklist to guide the staged rollout of the fee rounding change.

## Pre-Deployment (Before Day 1)

- [ ] Code review completed for pricing.js changes
- [ ] Both `feeMinor()` (new) and `feeMinorLegacy()` (rollback) functions are present
- [ ] Feature flag system is operational and tested
- [ ] Staging environment is ready for canary testing
- [ ] Finance team is prepared and standing by for Day 1 validation
- [ ] Support team is briefed on the change (no customer comms needed unless issues arise)

## Day 1: Canary Deployment

- [ ] Deploy to staging with new fee calculation enabled
- [ ] Generate 100+ test invoices using both algorithms
- [ ] Finance team manually verifies sample invoices
- [ ] Calculate: % of invoices affected, max delta, total variance
- [ ] Document: actual vs expected rounding differences
- [ ] **Decision point:** Does finance approve Phase 2 start?
  - [ ] Yes → proceed to 10% production rollout
  - [ ] No → identify issue and revert code, re-test

**Validation Threshold:**
- All invoices must generate successfully
- Rounding delta must be < 1 cent per invoice
- Batch variance must be < 0.1% of total invoice value
- Finance signs off in writing

## Days 2-7: Staged Production Rollout

### Day 2: 10% of Production Accounts
- [ ] Enable feature flag for 10% of accounts
- [ ] Monitor: invoice success rate (target: 99.9%+)
- [ ] Monitor: no error spikes in logs
- [ ] Check: support queue for fee-related complaints
- [ ] Verify: payment processor reconciliation runs successfully
- [ ] Wait: 24 hours for full batch cycle

### Day 4: Expand to 25%
- [ ] Review: metrics from 10% cohort (clean?)
- [ ] Enable feature flag for 25% of accounts
- [ ] Repeat monitoring for 24 hours

### Day 6: Expand to 50%
- [ ] Review: metrics from 25% cohort (clean?)
- [ ] Enable feature flag for 50% of accounts
- [ ] Repeat monitoring for 24 hours

## Day 8+: Full Deployment

- [ ] Review: metrics from 50% cohort (clean?)
- [ ] Confirm: no customer support escalations
- [ ] Confirm: payment processor reconciliation is clean
- [ ] Remove feature flag (100% of accounts now use new calculation)
- [ ] Legacy code remains in codebase for historical re-processing
- [ ] Post-deployment monitoring for 1 week

## Emergency Rollback Procedures

**If issues detected at ANY point:**

### Option 1: Environment Variable (Fastest)
```bash
kubectl set env deployment/ledger-api DISABLE_NEW_FEE_ROUNDING=true
kubectl rollout status deployment/ledger-api
```
- Impact: All new invoices use legacy calculation immediately
- Data: Already-generated invoices unchanged
- Recovery: Re-run invoices with legacy calculation in batch process

### Option 2: Feature Flag Rollback (Targeted)
```bash
# Disable for affected accounts in feature flag system
# Immediate effect on next invoice generation
```
- Impact: Only specific accounts revert to legacy
- Data: Already-generated invoices unchanged
- Recovery: No batch re-run needed if only subset affected

### Option 3: Code Rollback (Code change)
```bash
git revert <commit-hash>
# Build and deploy
kubectl rollout status deployment/ledger-api
```
- Impact: Full rollback to previous code
- Data: Already-generated invoices unchanged
- Recovery: Same as Option 1

**Post-Rollback:**
- [ ] Notify finance of rollback and reason
- [ ] Investigate root cause
- [ ] Plan remediation or hold release
- [ ] Consider extended canary testing before retry

## Metrics to Monitor

**Real-time (during rollout):**
- Invoice generation success rate (% success)
- Error rate (HTTP 5xx, exceptions in logs)
- Processing latency (p50, p95, p99 time to generate invoice)

**Daily (end of business):**
- Total invoices generated by algorithm (new vs legacy count)
- Sample of fee amounts: confirm rounding looks correct
- Payment processor reconciliation: pass/fail
- Customer support tickets mentioning fees: count and summary

**Post-deployment (1 week):**
- No regression in any metrics
- Reconciliation remains clean
- No customer churn spike
- No surge in support tickets
